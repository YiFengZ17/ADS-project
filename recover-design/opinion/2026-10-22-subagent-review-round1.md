当前论文已经足够简明，不能靠继续删掉证明或计时边界来提高质量。最值得完善的是第 3.2 节的失败分支证据。代码现有 935 个测试确实触发回滚，但只在两个可行 4×4 输入上各回滚一次；不能声称“完全未测回滚”，也不能把这两次回滚扩写为充分的复杂失败路径覆盖。

候选边建模与代码一致：同一行列相邻连接器之间建边；每个空格至多记录一条水平和一条竖直候选边；仅禁止空格处相交。传播规则是必要条件，分支尝试两个布尔值，`trail` 记录首次赋值，父层在子调用失败后回到保存的位置。成功叶子已经传播到稳定状态，所有边已确定，满足度数及交叉条件。未发现合法输入上的具体错误反例。未声称证明隐藏评测接受或性能足够。

## 命令、结果与实际覆盖

以下命令工作目录为 `recover-design/TA/`：

```bash
g++ -std=c++17 -O2 -Wall -Wextra -Wpedantic code/main.cpp -o build/recover-design
python3 scripts/check.py --binary build/recover-design
g++ -std=c++17 -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer -fno-pie -no-pie code/main.cpp -o build/recover-design-san
python3 scripts/check.py --binary build/recover-design-san
```

两种构建均实际输出：`PASS: 935 solver cases; 3 validator rejection checks`。编译未出现警告，未观察到 sanitizer 错误。

为了检验分支覆盖，仅复制源码至 `qa/instrumented.cpp`，在 `search` 入口、传播失败和 `rollback` 入口加计数器，退出时向 stderr 输出计数；复制检查器至 `qa/check_instrumented.py`，读取计数，单次 solver 超时由 15 秒改为 3 秒，其余输入生成与验证不变。此修改不改变选边、传播、回滚和结果判定逻辑。

```bash
g++ -std=c++17 -O2 qa/instrumented.cpp -o build/instrumented
python3 qa/check_instrumented.py --binary build/instrumented
```

实际输出：

```text
PASS: 935 solver cases; 3 validator rejection checks
calls/fails/rollbacks [2224, 814, 2] covered 814
rollback examples [([4, 1, 1], [[1, 2, 0, 2], [0, 2, 0, 3], [1, 3, 2, 3], [0, 1, 1, 1]]), ([4, 1, 1], [[0, 0, 1, 1], [0, 2, 2, 0], [1, 2, 2, 1], [0, 1, 2, 1]])]
```

其中 `fails` 统计传播返回失败，`covered` 统计出现传播失败或回滚的输入数，并不等于回滚输入数。两个回滚输入分别有 4 次 search 调用、1 次传播失败、1 次 rollback。其余失败发生在根调用。两个输入均为现有随机生成的可行案例，所有回滚计数合计只有 2，因而没有任何节点两条分支都失败后的双回滚。上述审核文件可本地复跑；未增加漫长压力测试。

题面与检查器相互一致。小规模 oracle 对候选子集做穷举，区别于求解器的传播加回溯；输出验证通过网格追踪方向而非读取 solver 内部数据。100 个构造可行案例删除零度候选点后，保留边仍不跨越已存在的连接器，因此其预期可行性合理。

计时边界按代码核对：`perf_counter` 位于输入序列化及 `subprocess.run` 前，停止于返回码、stderr 和 Python 输出验证之后；每次测量均为新进程。PDF 第 3.3 节明确写出启动、输入输出、求解和 Python 验证，未误写成纯算法耗时。未重跑 benchmark 或替换历史数值；没有提交历史 timings.json 不是扣分项。
