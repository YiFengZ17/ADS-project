## 代码审阅（opinion/README 列出的重点）

1. **上界剪枝不会删掉更优解。** `dp_bounds` 的上界是按效率排序后，对剩余物品 j+1..n 做 LP 松弛并向下取整；只有 `bound > z` 的状态被保留，而 `z` 始终是某个可行解的利润。逻辑正确。
2. **溢出。** 前缀和至多约 $10^{16}$，`W[j] + (c - s.w)` 至多约 $10^{18}+10^{16}$，仍在 `long long` 范围内；效率比较和插值用 `__int128`。未发现溢出风险。
3. **Bonus 方法的范围。** 删除重量上限为 `min(2w², 前缀重量)`，增加重量上限为 `min(2w² + Δ, 其余总重量)`，与"至多改动 2w 个物品、每个重量至多 w"的邻近性结论一致；最终解的重量 = 前缀重量 − k + 增加重量 ≤ c。
4. **SMAWK 的使用条件。** b 是按利润降序的前缀和，是凹序列；矩阵 a[j] + b(i−j) 满足 Monge 条件（行最大值位置单调不减）。NEG 用只与列有关的常数代替，不破坏这一性质；b 在定义域外用很陡的斜率延拓，保持凹性。条件成立。
5. 未发现会导致错误结果的代码问题，结论与上面两组独立对照一致。

## 计时复现：发现的问题

### 问题 1：生成器在不同标准库下产生不同数据（影响可复现性）

`code/gen.cpp` 用 `std::uniform_int_distribution` 取随机数。C++ 标准只规定它的分布，不规定算法，所以 GCC 的 libstdc++ 和 Apple Clang 的 libc++ 用同一个种子会得到不同的数据。复现时用 libc++ 另编一份生成器核对：

- `gen 5 1000 uncorrelated 1` 在两个标准库下输出完全不同（libstdc++：`5 989 / 134 137 / ...`；libc++：`5 1401 / 873 591 / ...`）。
- 用 libc++ 生成的数据，实验 1（n=1000）报告中的 7 个 work 值全部复现（如 uncorrelated 的上界剪枝方法为 1,946 / 1,848 / 4,192 个状态，中位数 $1.9\times10^3$）。说明算法本身是确定的，报告数据在 libc++ 上可复现。
- 用 Linux / GCC 生成的数据，同一单元格的 work 不同（上界剪枝 uncorrelated 中位数为 $7.4\times10^3$，strong 为 $3.8\times10^6$，报告为 $6.4\times10^6$），依赖具体输入的说法也不再成立。例如报告称实验 3 中 inverse、$n=10^6$ 的三个输入有两个只需 41 ms，而在 GCC 数据上三个输入分别为 0.81 s、7.5 s、6.3 s。

因此 `TA/README.md` 和报告中"同样的参数总是生成同样的输入"的说法，只在同一个标准库下成立。

**建议：** 在 `gen.cpp` 里自己写一个整数取值函数（例如对 `mt19937_64` 的输出做拒绝采样或直接取模），不依赖 `uniform_int_distribution`，使任何平台都生成同一份数据；改动后需要重跑实验并更新表格和图。如果不改代码，至少在 README 和报告的 Test Data 一节写明"数据依赖标准库，报告数据由 Apple Clang / libc++ 生成"。

### 问题 2：500 ms 跳过阈值与机器有关，较慢的机器上关键结论跑不出来

`scripts/benchmark.py` 在某算法的中位数超过 500 ms 后不再测更大规模。复现机器比作者机器慢约 2.5 倍（DP-1 每个表项约 0.7 ns，报告为 0.28 ns），列表法在实验 2 的 R=$10^3$ 时已达 697 ms，于是 R≥$10^4$ 被跳过。而报告"容量很大时列表法比 DP-1 快约 250 倍"的结论正好在这一段，直接运行 `make benchmark` 无法复现。

复现者手动补测（GCC 数据，n=1000，uncorrelated）：R=$10^4$、$10^5$、$10^6$ 时列表法分别约为 0.89–0.98 s，状态数稳定在约 $4\times10^7$；DP-1 在 R=$10^4$ 时为 1.66–1.79 s，按线性外推到 R=$10^6$ 约 170 s，约为列表法的 190 倍。交叉点同样在 R=$10^3$ 到 $10^4$ 之间，结论成立。

**建议：** 跳过规则改用与机器无关的 work（例如状态数或表项数超过某个值），或者实验 2 对列表法不跳过；也可以在 README 中说明较慢的机器需要调大 `SKIP_MS`。

### 问题 3：摘要中的绝对时间只对作者机器成立

摘要写"the bonus method solves $10^6$ items ... in less than 90 ms on every type"，复现机器上为 147–236 ms。**建议**写成"on our machine"，或改成相对说法（例如"time almost does not change from $10^3$ to $10^6$ items"）。
